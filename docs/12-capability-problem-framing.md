# 12 — Capability 02: Problem Framing

**وضعیت:** FINAL  
**تاریخ تثبیت:** 2026-10-04

## تعریف

> **Problem Framing توانایی تبدیل یک وضعیت مبهم، شکایت، KPI خراب یا درخواست راه‌حل به مسئله‌ای دقیق، قابل بررسی و قابل تصمیم است.**

اصل:
> پرچمدار قبل از اینکه بپرسد «چه بسازیم؟» می‌پرسد «چه مسئله‌ای واقعاً ارزش حل‌کردن دارد؟»

## زنجیره استاندارد Framing

**Signal → Observation → Problem → Evidence → Root Cause Hypotheses → Affected User → Impact → Problem Statement**

فرد باید Solution را از Problem جدا نگه دارد.

## خطاهای اصلی

1. Solution-first thinking
2. Symptom = Problem
3. Problem too broad
4. Assumption as fact
5. Internal problem disguised as customer problem

## Mission Ladder

### M1 — The Solution Request
کاندیدا یک درخواست مستقیم برای ساخت راه‌حل دریافت می‌کند.

هدف:
- مقاومت حرفه‌ای در برابر Solution Jumping
- پرسیدن Why / For whom / Desired behavior / Evidence / Cost of inaction

### M2 — The Bad Metric
یک KPI افت کرده اما Problem واقعی هنوز مشخص نیست.

هدف:
- Breakdown کردن Metric
- درخواست داده تکمیلی
- محدودکردن Problem به Segment/Context واقعی

### M3 — The Loud Customer
یک مشتری بزرگ یا ذی‌نفع پرصداتر Feature مشخصی می‌خواهد.

هدف:
- تشخیص Representativeness
- کشف Underlying Need
- جداکردن Stakeholder Request از User Problem

### M4 — Conflicting Evidence
منابع مختلف شواهد متناقض ارائه می‌دهند.

هدف:
- مدیریت ابهام
- وزن‌دهی به Evidence
- نادیده‌نگرفتن داده مخالف
- اصلاح Frame با شواهد جدید

### M5 — Find the Problem
به فرد فقط یک Business Area داده می‌شود و باید خودش مسئله ارزشمند را کشف کند.

هدف:
- Problem discovery
- Impact sizing
- Segment selection
- انتخاب مسئله‌ای که ارزش حل‌کردن دارد

## Artifactهای اصلی

- Problem Brief
- Evidence Map
- Problem Tree
- Affected Segment Definition
- Impact Estimate
- Assumption Log
- Problem Statement

## قالب استاندارد Problem Statement

> **[Who] در [Context] برای انجام [Desired Progress] با [Observed Problem] مواجه است که طبق [Evidence] باعث [Impact] می‌شود. علت اصلی هنوز [Known / Hypothesis / Unknown] است.**

این قالب ابزار Discipline است و نباید به Form-filling تبدیل شود.

## معیار کفایت Framing

قبل از ورود به Solution Space باید بتوان به این سؤال‌ها پاسخ داد:

- چه کسی مشکل دارد؟
- کجا رخ می‌دهد؟
- دقیقاً چه اتفاقی می‌افتد؟
- از کجا می‌دانیم؟
- چقدر مهم است؟
- چه چیزهایی هنوز نمی‌دانیم؟

داشتن پاسخ برای «راه‌حل چیست؟» در این مرحله الزامی نیست.

## Red Flagها

- عاشق‌شدن سریع به Solution
- تعریف Problem با نام Feature
- استفاده از Anecdote به‌عنوان Fact
- نادیده‌گرفتن Evidence مخالف
- سؤال‌نپرسیدن
- رفتن مستقیم سر PRD
- تغییر Problem برای توجیه راه‌حل مورد علاقه
- Confuse کردن Stakeholder Request با User Need
- Data dumping بدون Insight

اصل:
> هرجا کسی گفت «همه می‌دانیم مشکل چیست»، باید پرسید: «از کجا می‌دانیم؟»

## نقش Parcham AI

### Learn Mode
آموزش تفاوت Symptom، Problem، Cause، Root Cause، Evidence و Assumption.

### Practice Mode
Challenge کردن Frame:
- این Fact است یا Assumption؟
- اگر این داده غلط باشد، Frame چه تغییری می‌کند؟
- Solution را حذف کن؛ حالا Problem چیست؟

### Assessment Mode
AI فقط نقش World / Stakeholder / Data Source را دارد و نباید Problem را برای فرد کشف کند.

اطلاعات مرتبط فقط وقتی ارائه می‌شود که کاندیدا سؤال یا درخواست مناسب مطرح کند.

## Evidence

فقط Problem Statement نهایی ارزیابی نمی‌شود. مسیر رسیدن به آن نیز Evidence است:

- سؤال‌های مطرح‌شده
- اطلاعات درخواست‌شده
- Hypothesisها
- Hypothesisهای ردشده
- واکنش به Evidence مخالف
- Revision History

## شرایط عبور

برای عبور، فرد باید در چند Context مختلف نشان دهد که:
- Solution Request را بدون بررسی به Problem تبدیل نمی‌کند؛
- Fact و Assumption را جدا می‌کند؛
- Evidence مرتبط جمع می‌کند؛
- User/Segment را دقیق می‌کند؛
- Problem را به‌اندازه قابل تصمیم محدود می‌کند؛
- با داده جدید Frame را اصلاح می‌کند؛
- پیش از ورود به Solution Space یک Problem قابل دفاع ارائه می‌دهد.

در حداقل یک Mission باید Evidence روشنی وجود داشته باشد که فرد **فرضیه اولیه خودش را با Evidence جدید کنار گذاشته یا اصلاح کرده است**.

اگر فرد همیشه اولین برداشت خودش را «درست» اعلام کند، Problem Framing هنوز به‌طور کافی اثبات نشده است.
